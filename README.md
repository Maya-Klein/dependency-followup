# Dependency Follow-up Assistant

כלי למעקב אחר נושאים שממתינים לגורמים אחרים (ספק, עמית, רשות). לכל נושא יש מועד יעד, והקוד מחשב ממנו כמה ימים נותרו ומסמן את הנושא באחת מחמש דרגות דחיפות. הממשק בעברית, מימין לשמאל.

הפרויקט בנוי בשלבים קטנים. כרגע מומש **שלב 1 (שער 1)**: שמירת מועד והצגתו בצבע לפי הימים שנותרו. האפיון ב-[`docs/spec.md`](docs/spec.md) והתוכנית המלאה ב-[`docs/plan.md`](docs/plan.md).

## דרגות הדחיפות

הספים מוגדרים פעם אחת, ב-`app/core/deadlines.py`. הימים הם ימים קלנדריים לפי תאריך בלבד, בשעון ישראל (`Asia/Jerusalem`).

| ימים שנותרו | דרגה | תווית |
|---|---|---|
| 6 ומעלה | `far` | בהמשך |
| 2–5 | `approaching` | מתקרב |
| 1 | `tomorrow` | מחר |
| 0 | `today` | היום |
| פחות מ-0 | `overdue` | באיחור |

## ארכיטקטורה

שלוש שכבות עם תלות חד-כיוונית, כך שאפשר להחליף את הממשק בלי לגעת בלוגיקה:

```
web  ──►  core      (לוגיקה טהורה, בלי Flask ובלי DB)
 │
 └─────►  storage   (SQLAlchemy Core, SQLite)
```

| רכיב | קבצים | תפקיד |
|---|---|---|
| `app/core/` | `deadlines.py` | חישוב ימים שנותרו (`days_remaining`), דרגת הדחיפות (`urgency_level`), הניסוח העברי (`days_text`) ו"היום" בשעון ישראל (`today_in_israel`). פונקציות טהורות שמקבלות `today` כפרמטר, ולכן הבדיקות דטרמיניסטיות. |
| `app/storage/` | `db.py`, `repository.py` | הגדרת טבלת `topics` ופונקציות `add_topic` ו-`list_topics`. החיבור נקבע ב-`DATABASE_URL` (ברירת מחדל `sqlite:///data/app.db`). כותרת ריקה או ארוכה מ-200 תווים נדחית. |
| `app/web/` | `__init__.py`, `routes.py`, `templates/`, `static/` | אפליקציית Flask: `create_app()`, נתיבי `GET /` ו-`POST /`, ותבניות Jinja2 עם escaping אוטומטי. |
| `run.py` | | הפעלת השרת המקומי על `127.0.0.1:5000`. |
| `tests/` | | pytest לכל שלוש השכבות. |

## זרימת הנתונים

**הוספת נושא (`POST /`):**
1. הטופס שולח כותרת ותאריך.
2. ה-route בודק את התאריך ואת אורך הכותרת. `add_topic` מסיר רווחים בקצוות ודוחה כותרת ריקה.
3. הנושא נשמר בטבלת `topics`.
4. הדפדפן מופנה ל-`GET /` (redirect 303). בשגיאה חוזר הדף עם קוד 400 והודעה בעברית, וההזנה נשמרת.

**הצגת הרשימה (`GET /`):**
1. `list_topics` שולף את הנושאים ממוינים לפי מועד.
2. לכל נושא, `days_remaining` מחשב את הימים שנותרו מול `today_in_israel()`, ו-`urgency_level` קובע את הדרגה.
3. התבנית מציגה כותרת, תאריך, ניסוח הימים ותווית, עם מחלקת CSS `level-<דרגה>`. הצבע לא נושא את המידע לבדו, כי יש גם תווית טקסט.

הדחיפות מחושבת בקוד בלבד.

## התקנה

דרוש Python 3.9 ומעלה (נבדק רק עם 3.14).

```
git clone https://github.com/Maya-Klein/dependency-followup.git
cd dependency-followup
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
```

בלינוקס ובמק משתמשים ב-`.venv/bin/python` במקום `.venv\Scripts\python`. החבילה `tzdata` ברשימה כי ב-Windows אין מאגר אזורי זמן מובנה.

## הרצה

```
.venv\Scripts\python run.py
```

האפליקציה זמינה ב-http://127.0.0.1:5000. קובץ ה-DB נשמר ב-`data/app.db` (לא עולה לגיט). אפשר לשנות אותו עם המשתנה `DATABASE_URL`.

## בדיקות

```
.venv\Scripts\python -m pytest
```

הבדיקות מכסות את ערכי הקצה של הדרגות, מעברי חודש ושנה, אזור זמן סביב חצות, שמירה ושליפה מחיבור חדש, כותרת ריקה או ארוכה מדי, תאריך לא תקין וכותרת עם קוד HTML שמוצגת כטקסט.

## מה האפליקציה עושה ומה לא

**עושה (שלב 1):**
- שומרת נושא עם כותרת ומועד יעד.
- מחשבת בקוד כמה ימים נותרו (ימים קלנדריים, שעון ישראל) ומסמנת את הנושא באחת מחמש דרגות, עם צבע ותווית טקסט.
- מציגה את הרשימה ממוינת לפי מועד. הכותרת מוצגת כטקסט, גם אם היא כוללת HTML.

**לא עושה (עדיין):**
- אין סטטוס פתוח/סגור, תוצאה נדרשת, אבן דרך או עריכה של נושא.
- אין היסטוריית עדכונים ואין ניתוח AI של שרשורים.
- אין התחברות, כמה משתמשים או פריסה לענן. משתמש יחיד על `127.0.0.1`.

## מגבלות ידועות

- העיצוב מ-Stitch עדיין לא הוטמע בתבניות. הדף הנוכחי הוא הגרסה הראשונית משלב 1.
- אין הגנת CSRF בטפסים. זה מקובל ב-MVP (משתמש יחיד, האזנה מקומית בלבד) וצריך להוסיף אותה לפני התחברות או פריסה.
- ימים נספרים לפי לוח שנה בלבד, בלי ימי עבודה, סופי שבוע או חגים.
- ספי הדרגות קבועים בקוד ואינם ניתנים להתאמה.
- שינויי סכמה בשלבים הקרובים ידרשו מחיקה של קובץ ה-DB המקומי (`data/app.db`).
- `pip-audit` הורץ על `requirements.txt` (19.10.2026) ולא נמצאו פרצות ידועות. כדאי להריץ אותו שוב כשמוסיפים תלויות.
- מסכי מצבי הקצה והמחשב ב-Stitch לא אומתו. אושר רק מסך הנייד.

## הצעדים הבאים

לפי [`docs/plan.md`](docs/plan.md), שלב אחד בכל פעם:

1. **שלב 2 (בעבודה):** הטמעת העיצוב מ-Stitch ב-`app/web/templates/` וב-`style.css` בלבד. 56 הבדיקות הקיימות צריכות לעבור בלי שינוי, וצריך לעדכן את ניסוח הימים ל"בעוד יום" ו"לפני יום".
2. **שלב 3:** נושא מלא: תוצאה נדרשת, אבן דרך וסטטוס פתוח/סגור.
3. **שלב 4:** היסטוריית עדכונים מתוארכת, שלא נדרסת.
4. **שלב 5:** תרחישים סינתטיים ובדיקות לחלק שאינו AI.
5. **שלב 6:** ניתוח שרשור ב-AI, מבודד ובלי ממשק, עם אימות ציטוטים בקוד.
6. **שלב 7:** חיבור הניתוח לאפליקציה ושער 3.

רעיונות מחוץ ל-MVP מרוכזים בסעיף "בהמשך" ב-`docs/plan.md`.

## עיצוב

העיצוב נעשה ב-Stitch (פרויקט "מעקב תלויות – שער 1 (סופי)"): Rubik, RTL, פינות 8px, כרטיס לכל נושא עם פס צבע של 6px בצד ימין, ותגית עם טקסט בכל דרגה כך שהצבע אינו האות היחיד. "היום" מוצג בתגית עם מסגרת ואייקון שעון, ו"באיחור" בתגית מלאה עם אייקון אזהרה, כדי שיהיה קל להבדיל ביניהם. בנייד הרשימה קודמת, והטופס נפתח מהכפתור "+ הוספת נושא" (`details/summary`, בלי JavaScript).

## תהליך הפיתוח והכלים

- **חלוקת מודלים:** תכנון עם Opus וביצוע וכתיבת קוד עם Sonnet.
- **שלבים קטנים:** שלב אחד בכל פעם, לפי התוכנית. תוכנית לכל שינוי לא טריוויאלי, ואישור לפני ביצוע.
- **בדיקות:** pytest מקצה לקצה, מקרי קצה ורגרסיה אחרי כל שלב, ותיקון כשלים לפני שממשיכים.
- **סקירת אבטחה:** אחרי כל שלב (הזרקה, קלט, סודות, חשיפת מידע). ממצאים מדווחים ומתוקנים רק באישור.
- **גיט:** ענף חדש לכל פיצ'ר, אף פעם לא commit ישיר ל-`main`, ו-commit אחרי כל פעולה שהושלמה.
- **אובסידיאן:** יומן עבודה בכספת, בתיקייה `dependency-followup`. `Stop` hook (`.claude/settings.json` ו-`.claude/hooks/log_task.py`) מוסיף בסוף כל סבב רשומה קצרה עם ענף, commit וסיכום. רשומות מפורטות (החלטות, בעיות פתוחות, צעד הבא) נכתבות ביד.
- **GitHub CLI (`gh`):** פתיחה ומיזוג של pull requests מהטרמינל.
- **Stitch MCP:** יצירת העיצוב ו-design system ישירות מ-Claude Code.
- **Obsidian MCP:** קריאה וכתיבה בכספת מתוך הסשן.
- סקילים שהשתמשתי בהם: security-review
